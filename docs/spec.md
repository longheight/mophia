## 1. スコープの決定方針

このプロジェクトの最大のリスクは **「映像の動きから音楽そのものを自動生成する」機能が技術的に未検証・方針未定であること**。ここを開発期間の後半まで先送りにすると、1月末の展示に間に合わない可能性が高い。
したがって、**v1(展示版)のスコープを意図的に絞り込む**。自動作曲は展示後の発展課題とし、今回は「映像そのものを解析してUI/エフェクト/譜面を生成する」部分に集中する。

## 2. システム仕様

### 2.1 対応する映像

- **v1で対応**: 音源(BGM・環境音などプレイに使える音)が既に含まれている動画。実写・モーショングラフィックス問わず対応する。
- **v1で対応しない**: 無音、または音楽的に使えない音声のみの動画から音楽を自動生成する機能。技術検証にかかる工数が読めないため、v1のスコープからは外す。
- **フォールバック**: 送信された動画に使える音源がない場合、あらかじめ用意した汎用BGM数種の中から自動選択してゲームを生成する(処理を止めない)。
- **入力制約**: 最大尺 30秒(展示体験のテンポと解析時間を両立させるため。技術検証の結果次第で見直し)。ファイル形式はスマートフォンの標準出力形式(mp4/mov)を想定。

### 2.2 処理パイプライン

現行構成(OpenCV・SAM2・PyTorchによる映像/音楽解析 → Python で譜面データをJSON書き出し → Unity(C#)で読み込み・実行)を踏襲し、実写映像にも通用するよう解析ロジックを拡張する。

```
User(スマホ) → 動画アップロード(Web) → 解析サーバー(OpenCV/SAM2/PyTorch, Python)
            → 譜面JSON → Unity(C#) → 筐体ディスプレイ上で音楽ゲームとして実行
```

### 2.3 送信システム(動線)

- 筐体に **QRコード** を掲示し、来場者は自分のスマホで読み取って専用アップロードページを開く。
- アップロードページで動画を選択・送信 → サーバー側で解析開始。
- 処理中は筐体側に「解析中」の待機演出を表示する(体感待ち時間の緩和)。
- 目標処理時間: 送信から再生開始まで **60秒以内**(展示の回転率を確保するための目安。技術検証フェーズで実測して見直す)。

### 2.4 操作フィードバック: グラフィックス×実写の合成 (2026-10-22 追加)

コンセプト資料 (`mophia_concept_3.pdf`) に基づく仕様変更。

#### 2.4.1 変更内容

| | 変更前 | 変更後 |
|---|---|---|
| 判定成功時のフィードバック | SAM2で切り抜いた実写の連番をそのまま再生(`EffectPlayer`) | 実写の切り抜きと、入力映像に合わせて選んだ**モーショングラフィックス**を合成したアニメーションを再生 |
| 見た目のねらい | 「自分の映像が動く」 | 「自分の映像がどんなビジュアルになるのか」というワクワク感。音・ビジュアル・操作の一体感 |

参考イメージ(資料 p.1): 鳥の切り抜き+円・輪・矩形・線、手の切り抜き+放射線・カラフルな小片、人物の切り抜き+帯状の曲線・ハーフトーンのドット。いずれも**実写は被写体だけを切り抜き、その前後に平面的な幾何学図形を重ねる**コラージュ調。

#### 2.4.2 実装方針

**(a) グラフィックスは「テンプレート+パラメータ」の手続き生成とする(生成AIは使わない)**

- 理由: 処理時間目標(60秒)に収まり、見た目の品質を作り手側で管理できる。参考イメージの語彙(円・線・矩形・放射線・帯・ドット)は手続き生成で十分表現できる。
- v1のテンプレート(叩き台。参考イメージから抽出):

  | テンプレート | 図形の語彙 | 向いている被写体・音 |
  |---|---|---|
  | `orbit` | 塗り円+輪郭円が被写体の周囲に配置され、ゆっくり回る・広がる | 丸い形状 / 動きが穏やか |
  | `frame` | 矩形の枠と水平・垂直の線が被写体に追従して伸びる | 角ばった形状 / 動きが穏やか |
  | `burst` | 被写体の一点から放射線とカラフルな小片が弾ける | アタックの強い音(flick相当) |
  | `ribbon` | 帯状の曲線が被写体の背後を流れ、ドットが散る | 持続する音(long相当) |
  | `trail` | 被写体の移動方向に沿って線・図形が残像のように流れる | 移動量が大きい被写体 |

**(b) 選択ロジックは既存の `feature_decider.py` を拡張する**

`mophia_convert` の `feature/ioi-NoteType` ブランチで実装済みの特徴量をそのまま入力に使う。新しく解析する必要があるものはほぼない。

| 特徴量(既存) | 使い道 |
|---|---|
| 円形度(round/sharp) | 図形の語彙(円系 / 矩形・線系) |
| 重心の軌跡(移動量・方向) | `trail` の判定と流れる向き |
| 面積の変化(shrink/spread) | 図形が収束するか広がるか |
| noteType(tap/flick/long) | `burst` / `ribbon` などの判定 |
| 前景色(primary/secondary) | 配色(下記) |

- **配色**: 被写体の主要色からトーンを落としたベース色(参考の鳥の例でいうスレートブルー)と、それに対するアクセント色1〜2色を作る。彩度の低い被写体では、セクションの代表色にフォールバックする。
- **目印との統一**: 判定前の目印(`IndicatorController` のpreset)とフィードバックのグラフィックスで、配色と図形の語彙(round/sharp)を揃える。目印が判定後にそのままフィードバックへ「育つ」ように見せ、操作と見た目をつなげる。
- 同じ動画なら毎回同じ結果になるよう、ノートごとに乱数の `seed` を譜面に書き出す。

**(c) 合成(描画)はUnity側で実行時に行う。Pythonはパラメータを決めるだけにする**

| | Python側で合成済みの連番を書き出す | **Unity側で実行時に描画(採用案)** |
|---|---|---|
| 処理時間 | ノート数×フレーム数の描画・PNG書き出しが増え、60秒目標を圧迫する | 増えない(JSONにパラメータを足すだけ) |
| 判定ランクへの反応 | できない(事前に焼き込むため) | できる(Perfectは派手に、Goodは控えめに、など) |
| 既存資産 | `EffectPlayer` を変えずに済む | `IndicatorController` (DOTween) の作り方をそのまま流用できる |
| 調整のしやすさ | Pythonだけで確認できる | Unityで確認する必要がある → 調整用シーンを用意して補う |

- 描画レイヤー構成: **背面グラフィックス(塗りの図形) → 実写の切り抜き → 前面グラフィックス(細い線・輪・小片)**の3層。前後に挟むことで、参考イメージのような「図形と被写体が絡み合う」奥行きを出す。
- グラフィックスは被写体に追従させる。そのために、切り抜き連番の各フレームについて、**元映像座標での被写体の位置・大きさ**(bbox、重心)を `offset.json` に追加して出力する(現在はアトラス上の座標しかない)。
- 判定ランクの扱い(叩き台): Perfect=全レイヤーをフル再生 / Great=前面レイヤーを省略 / Good=背面レイヤーのみ / Miss=フィードバックなし。

**(d) 譜面JSONへの追加(案)**

ノートごとに `feedback` を追加する。最終的な形は、実装着手時に `docs/chart-schema.md` で確定させる(→ [workflow.md](workflow.md) の「譜面フォーマットを契約にする」)。

```json
"feedback": {
  "template": "orbit",
  "shape": "round",
  "palette": { "base": [0.45, 0.53, 0.60, 1.0], "accents": [[0.95, 0.42, 0.20, 1.0]] },
  "direction": 135.0,
  "intensity": 0.8,
  "seed": 1234
}
```

#### 2.4.3 スケジュールへの影響

- Phase 1(〜11/1)内で、**テンプレート1種(`orbit`)を Unity の調整用シーンで動かし、見た目の方向性を確認する**ところまでを行う。
- 残りのテンプレートと選択ロジックは Phase 2 の「実写対応のコア実装」(11/15)に含める。11/22の早期統合テストの時点で、テンプレート3種以上が動いていることを目標にする。
- 不足する場合は、テンプレート数を減らして対応する(`orbit` / `burst` の2種でも体験は成立する)。

## 3. 筐体仕様

### 3.1 基本構造

コンセプト資料の透過ディスプレイ構造(前面ディスプレイ[カラーフィルター]・背面ディスプレイ・赤外線タッチスクリーンを柱で固定)を踏襲する。

### 3.2 サイズ・画面向き

- 一般的なアーケード音楽ゲーム筐体より小型のものを想定(白キューブ的なミニマルな展示空間に馴染むサイズ)。
- **画面向きは縦(ポートレート)を基本案とする**: 来場者が正面に立って両手で操作する体験、かつ省スペースの観点から。ただし10月の詳細設計フェーズで実機検証の上、最終決定する。
- 外形寸法は詳細設計フェーズ(Phase 1, 10月)で確定する。

### 3.3 スピーカー・QRスタンド

- スピーカーは筐体基部(ベース)に内蔵する方向で検討。
- QRコード掲示スタンドは筐体に一体化するか、独立スタンドにするかを詳細設計フェーズで決定する。

### 3.4 耐久性・安全性

- 不特定多数の来場者が繰り返しタッチする前提のため、配線の露出防止・パネルの固定強度・転倒防止(重心設計)を組み立て時に必ずチェックする。

### 3.5 製作方針

- 自作。既存プロトタイプ(2026年4月展示で使用したもの)の構造を流用・改修する。

## 6. v1スコープ外(展示後の発展課題)

- 無音・非音楽的な動画からの自動作曲
- 処理時間のさらなる短縮・大量同時アクセス対応
- 30秒を超える尺への対応
