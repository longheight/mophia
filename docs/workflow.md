# Mophia 開発ワークフロー (2026-10-22 案)

ソフトウェア開発の進め方を見直すための提案。**仕様 → 譜面フォーマット → 実装 → 統合確認**の順に変更を流し、「どれが最新か」「どこまで動くか」を誰が見ても分かる状態にすることを目的とする。

## 1. 現状の問題(2026-10-22時点で確認した事実)

| 問題 | 具体例 | 起きていること |
|---|---|---|
| 最新のコードがどこにあるか分からない | 最新の変換処理は `mophia_convert` の `feature/ioi-NoteType`(7/24)にあり、`main`(7/17)には入っていない | 最新を探すのに毎回ブランチを掘る必要がある |
| Unityクライアントが複数ある | `mophia_dmeo_1`(4月・`notes`+`timings`形式)、`mophia_01`(7月・`sections`形式)、`mophia_demo`(空) | どれが本線か分からない。統合時の作業量が読めない |
| 譜面フォーマットが一致していない | `sam2_demo_2.py` の出力は `sections[].notes[]` だが、`mophia_dmeo_1` の `Chart.cs` は `notes`+`timings` を読む | PythonとUnityのどちらかを変えると、もう一方が黙って壊れる |
| 検証用データが手元のPCにしかない | 切り抜き連番・mp4・`output*/` は `.gitignore` で除外されている | デスクトップPCがオフラインだと、外からは何も試せない |
| 環境を再現できない | 依存関係の一覧(`requirements.txt`)がなく、`ddc_onset`・SAM2チェックポイントの入手方法も書かれていない | 別のPC(展示用PCを含む)で動かすときに詰まる |
| 仕様と実装が連動していない | フィードバック仕様の変更がコンセプト資料(PDF)にしか書かれていない | 実装の「正解」が人の頭の中にしかない |

## 2. リポジトリの整理

**役割を固定し、本線は3つにする。**

| リポジトリ | 役割 | 本線ブランチ |
|---|---|---|
| `mophia` | 仕様・スケジュール・譜面フォーマットの定義(**唯一の正**) | `main` |
| `mophia_convert` | 解析パイプライン(Python) | `main` |
| Unityクライアント(1つに決める) | 筐体で動くゲーム本体 | `main` |

- Unityクライアントは **`mophia_01` を本線とする案**を推す(`sections`形式・preset・`IndicatorController` があり、現行の変換処理と一番近い)。`mophia_dmeo_1` の改善点(R3によるライフサイクル管理、HUD、オブジェクトプールなど)で必要なものは `mophia_01` に移植する。
- `mophia_dmeo_1` と `mophia_demo` は README に「旧版・参照用」と書いてアーカイブする(GitHubの Archive 機能。削除はしない)。
- まず `mophia_convert` の `feature/ioi-NoteType` を `main` にマージし、`main` = 最新の状態に戻す。

## 3. ブランチ・変更の流し方

1. **仕様を先に変える**: 挙動が変わる変更は、まず `mophia/docs/spec.md` を更新するPRを出す(今回のフィードバック変更がその例)。PDFのコンセプト資料は、要点を spec.md に転記する。
2. **譜面フォーマットを変えるなら、次に `docs/chart-schema.md` を更新する**(→ 4章)。
3. **実装**: `mophia_convert` / Unity それぞれで `feature/<内容>` ブランチを切って実装する。
   - 1ブランチは**1週間以内**にマージする(週次チェックポイントと揃える)。長く寝かせると今回のように本線から外れる。
   - マージはPR経由で行う。2人体制なので、相手のレビューは必須にせず「PRの説明に、何をどう確認したかを書く」ことを必須にする。
4. **統合確認**: 両側がマージされたら、固定サンプル(→ 5章)で端から端まで通し、結果を PR か週次メモに残す。

コミットメッセージ・コメント・ログ出力は、既存のコードに合わせて日本語でよい。

## 4. 譜面フォーマットを契約にする

PythonとUnityの間で一番壊れやすいのが譜面JSON。ここを「契約」として明文化する。

- `mophia/docs/chart-schema.md` に、全フィールドの意味・型・単位・番兵値(`-1.0` など)を書く。同じ内容を JSON Schema(`chart.schema.json`)としても置く。
- 譜面の `meta` に `schemaVersion` を入れる。Unity側は、対応していないバージョンを読み込んだら警告を出す。
- `mophia_convert` に、出力した `output.json` をスキーマで検証する処理を入れる(既存の `check_chart.py` を拡張する)。
- フォーマットを変えるときは、`chart-schema.md`・Python・Unity の3つを**同じ週のうちに**揃える。

## 5. 外からでも試せるようにする(検証データと環境)

今回のように「デスクトップPCがオフラインで何も試せない」状態を防ぐ。

**固定サンプルセットを作る**

- 実写3〜5本(鳥・手・人物など、コンセプト資料の参考に近いもの)+CG1本を「固定サンプル」として決める。
- それぞれについて、GPUを使う段の出力(切り抜き連番・`atlas.png`・`offset.json`・`output.json`)を保存し、Google Drive か GitHub Release の添付ファイルに置く(gitには入れない)。
- これがあれば、**GPUのない環境でも、SAM2より後ろの処理**(`feature_decider`・グラフィックスの選択・Unityでの表示)を試せる。

**GPUを使う段と使わない段を分ける**

- `sam2_demo_2.py` の中で集めている視覚特徴量(重心・面積・マスク)をファイル(`features.npz` など)に書き出す。
- `feature_decider.py` は、そのファイルを読んで単体で実行できるようにする。こうしておけば、特徴量の判定ロジックの調整にGPUが要らなくなる。

**環境を再現できるようにする**

- `mophia_convert` に `requirements.txt` と、`ddc_onset`・SAM2チェックポイントの入手手順を README に書く。
- 展示用PCへのセットアップ手順も同じ README に書く(Phase 3aで必要になる)。

## 6. 進捗管理

- 週次チェックポイント([schedule.md](schedule.md))の項目を GitHub の Issue にし、`mophia` リポジトリの Projects(ボード)で管理する。Issue には「完了の条件」を1行で書く(例: 「固定サンプル3本で `output.json` がスキーマ検証を通る」)。
- 実装のPRは、対応するIssueを本文で参照する。
- 毎週日曜(チェックポイントの日)に、ボードを見て遅れを確認する。遅れていれば、schedule.md の「バースト対応」かスコープ調整を判断する。
